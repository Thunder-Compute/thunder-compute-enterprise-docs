This page defines the vocabulary used across these docs and in the tooling itself.

## Core concepts

| Term | Meaning |
| --- | --- |
| **Workload** | Anything that calls CUDA, including a training job, an inference server, a notebook, or a batch script. Thunder treats a workload as the unit that acquires and releases a GPU. A workload does not have to be modified, containerized, or recompiled to run under Thunder. |
| **Utilization** | The share of time a GPU is actually executing work. A GPU can be *allocated* to a workload for hours while only being *utilized* for a fraction of that time. |
| **Oversubscription** | Allowing more workloads to exist than you have physical GPUs, with the expectation that they will not all need a GPU at the same instant. |
| **Oversubscription ratio** | Workloads divided by physical GPUs. A ratio of `1.5x` means six workloads are being served by four GPUs. |

## Individual units

| Term | Meaning |
| --- | --- |
| **Fleet** | All the GPU servers an operator has enrolled with Thunder. A fleet may span multiple data centers, but a given workload is only ever matched to a GPU inside its own zone. |
| **Zone** | A single locality whose machines can all reach each other over a common IP range, in practice a data center or network region. Servers in a zone form a mesh, and GPU access never crosses a zone boundary. |
| **Server** | A physical machine that has GPUs and contributes them to the pool. Servers run `thunderd`. |
| **Client** | A machine, VM, or container that runs workloads and is connected to servers through the network. Clients run `libthunder` and borrow GPUs from servers over the network. |
| **Thunder Registry** | The Thunder-operated management API. Registers servers and clients, issues their credentials, and lets a client discover the servers in its zone. It does not choose GPUs and is not in the data path. |
