Thunder installs into Kubernetes as a Helm chart that publishes GPU capacity through
Dynamic Resource Allocation (DRA), so a pod requests a virtual GPU the same way it
requests any other DRA device.

We are releasing a public Helm chart soon. This guide covers a full deployment with
the current chart. For how the chart is put together and why it is designed this way,
see [Kubernetes internals](/kubernetes-internals).

<Note>
  GPU servers still need the pinned NVIDIA driver and the Thunder-patched kernel
  module before they can serve capacity. See [Requirements](/requirements) and
  [NVIDIA driver setup](/nvidia-driver).
</Note>

To give KubeVirt virtual machines a Thunder GPU, complete this page first, then see
[KubeVirt](/kubevirt).

## Cluster setup

Thunder publishes zone GPU capacity as DRA consumable capacity, so several claims can
draw from one published pool. That behavior is behind the `DRAConsumableCapacity`
feature gate, which is off by default and must be enabled on the API server,
scheduler, controller-manager, and **every kubelet** before installing the chart.

The manifests in this guide use `resource.k8s.io/v1`, which requires Kubernetes
`1.34` or newer.

Kubernetes does not provide a cluster-scoped `kubectl` switch for feature gates, so
how you set it depends on your distribution. In every case the value is the same:

```text
--feature-gates=DRAConsumableCapacity=true
```

<Tabs>
  <Tab title="RKE2">
    Server config at `/etc/rancher/rke2/config.yaml`:

    ```yaml
    kube-apiserver-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    kube-scheduler-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    kube-controller-manager-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    kubelet-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    ```

    Worker config at `/etc/rancher/rke2/config.yaml`:

    ```yaml
    kubelet-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    ```

    Restart RKE2 on each node it applies to:

    ```bash
    sudo systemctl restart rke2-server
    sudo systemctl restart rke2-agent
    ```
  </Tab>

  <Tab title="K3s">
    K3s takes the same configuration keys as RKE2. Server config at
    `/etc/rancher/k3s/config.yaml`:

    ```yaml
    kube-apiserver-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    kube-scheduler-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    kube-controller-manager-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    kubelet-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    ```

    Agent config at `/etc/rancher/k3s/config.yaml`:

    ```yaml
    kubelet-arg:
      - "feature-gates=DRAConsumableCapacity=true"
    ```

    Restart K3s on each node it applies to:

    ```bash
    sudo systemctl restart k3s
    sudo systemctl restart k3s-agent
    ```

    <Note>
      K3s ships a single binary that embeds the control plane, so a server node needs
      both the control-plane arguments and `kubelet-arg` if it also runs workloads.
    </Note>
  </Tab>

  <Tab title="kubeadm">
    On each control-plane node, add the flag to the three static pod manifests in
    `/etc/kubernetes/manifests/`. For example, in `kube-apiserver.yaml`:

    ```yaml
    spec:
      containers:
        - command:
            - kube-apiserver
            - --feature-gates=DRAConsumableCapacity=true
    ```

    Repeat for `kube-scheduler.yaml` and `kube-controller-manager.yaml`. The kubelet
    restarts each static pod when its manifest changes.

    <Warning>
      If a component already has a `--feature-gates` flag, add to the existing
      comma-separated list rather than adding a second flag. A duplicate flag is
      ignored, and the component starts without the gate.
    </Warning>

    On every node, including workers, add the gate to the kubelet config at
    `/var/lib/kubelet/config.yaml`:

    ```yaml
    featureGates:
      DRAConsumableCapacity: true
    ```

    Then restart the kubelet:

    ```bash
    sudo systemctl restart kubelet
    ```

    For clusters you have not created yet, set the same values in the `kubeadm`
    configuration file used by `kubeadm init`, so new control-plane nodes and workers
    come up with the gate already enabled.
  </Tab>

  <Tab title="EKS, GKE, AKS">
    <Warning>
      Managed Kubernetes services do not currently support this deployment.
    </Warning>

    EKS, GKE, and AKS do not expose API server, scheduler, or controller-manager
    flags, so `DRAConsumableCapacity` cannot be enabled on the control plane. Setting
    it on self-managed node groups is not sufficient: without the gate on the API
    server, the capacity fields in a Thunder `ResourceClaim` are silently dropped, and
    without it on the scheduler, claims are never allocated against Thunder's shared
    slices.

    Use a self-managed cluster, or a provider-supported Kubernetes version where the
    required DRA behavior is already enabled by default. Run the verification below
    against any cluster you are unsure about; it answers the question directly.

    A [standalone deployment](/standalone) is the supported path on infrastructure
    where you control the machines but not the Kubernetes control plane.
  </Tab>
</Tabs>

### Verify the feature gate

Confirm the API server preserves DRA capacity requests. If the gate is missing, the
`capacity` block is stripped from the returned object:

```bash
kubectl apply --dry-run=server -o yaml -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: thunder-capacity-field-check
  namespace: default
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: thunder-vgpu
            allocationMode: ExactCount
            count: 1
            selectors:
              - cel:
                  expression: device.attributes["vgpu.thundercompute.com"]["gpu_type"] == "A6000"
            capacity:
              requests:
                vgpu.thundercompute.com/gpu_count: "1"
EOF
```

This confirms the API server only. The scheduler and every kubelet still need the same
feature gate in their component configuration, and a missing kubelet gate does not show
up until a pod tries to start on that node.

## Node labels

The daemonset schedules only onto Thunder GPU nodes. Each eligible node needs a
zone, an externally reachable IP label, and the Thunder node labels expected by
the chart.

The `external-ip` specified must be reachable within the zone it is in.
All nodes and clients running in that zone must be able to communicate with this IP address.

Required labels:

```bash
kubectl label node <node-name> thundercompute.com/node=true
kubectl label node <node-name> topology.kubernetes.io/zone=<zone-name>
kubectl label node <node-name> thundercompute.com/external-ip=<node-ip>
kubectl label node <node-name> nvidia.com/gpu.present=true
```

Verify node labels:

```bash
kubectl get nodes --show-labels | grep thundercompute.com/node
```

## Chart deployment

Install or upgrade the chart with a Kubernetes Secret containing the Thunder API
configuration. The API token must have the Thunder API read, create, and delete capabilities for
zones, nodes, clients, and enrollment tokens. See [Authentication](/authentication#claims).

Create the namespace and secret:

```bash
export THUNDER_API_TOKEN='<token>'

kubectl create namespace thunder-system \
  --dry-run=client -o yaml | kubectl apply -f -

kubectl -n thunder-system create secret generic thunder-api \
  --from-literal=THUNDER_API_TOKEN="${THUNDER_API_TOKEN}" \
  --from-literal=THUNDER_API_URL="https://api.thundercompute.com:2096" \
  --dry-run=client -o yaml | kubectl apply -f -
```

Apply the current CRDs before installing or upgrading the chart. Helm installs
CRDs on first install, but does not upgrade files in `crds/` during normal chart
upgrades.

```bash
kubectl apply -f charts/thunder-device-plugin/crds/
```

Install or upgrade the chart:

```bash
helm upgrade --install thunder-device-plugin charts/thunder-device-plugin \
  --namespace thunder-system \
  --set namespace.create=false \
  --set namespace.name=thunder-system \
  --set thunder.existingSecret=thunder-api
```

Verify rollout:

```bash
kubectl -n thunder-system rollout status deployment/thunder-device-plugin-operator
kubectl -n thunder-system rollout status daemonset/thunder-device-plugin
kubectl get deviceclasses thunder-vgpu
kubectl get resourceslices -l app.kubernetes.io/name=thunder-dra-driver
```

Confirm the published slices use shared consumable capacity. Empty output means the
chart is installed but the cluster is not honoring `DRAConsumableCapacity`:

```bash
kubectl get resourceslices -l app.kubernetes.io/name=thunder-dra-driver -o yaml \
  | grep -A12 allowMultipleAllocations
```

## Requesting GPUs from a pod

Pods should use `ResourceClaimTemplate`. Kubernetes creates a concrete claim for
each pod and deletes it with the pod. The container requests the claim through
`resources.claims`, and the daemon returns a claim-scoped CDI device during
prepare.

Pod request example:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: thunder-pod-gpu
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: thunder-vgpu
            allocationMode: ExactCount
            count: 1
            selectors:
              - cel:
                  expression: device.attributes["vgpu.thundercompute.com"]["gpu_type"] == "A6000"
            capacity:
              requests:
                vgpu.thundercompute.com/gpu_count: "1"
---
apiVersion: v1
kind: Pod
metadata:
  name: thunder-pod-gpu
spec:
  restartPolicy: Never
  resourceClaims:
    - name: vgpu
      resourceClaimTemplateName: thunder-pod-gpu
  containers:
    - name: tester
      image: ubuntu:24.04
      command: ["bash", "-lc", "nvidia-smi && sleep 3600"]
      resources:
        claims:
          - name: vgpu
            request: gpu
```

Apply and inspect:

```bash
kubectl apply -f pod.yaml
kubectl get pod thunder-pod-gpu
kubectl get resourceclaims
```
