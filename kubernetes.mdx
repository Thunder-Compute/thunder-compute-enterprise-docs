Thunder installs as a Helm chart that publishes GPU capacity through Dynamic Resource
Allocation (DRA). A pod requests a GPU by name, and Thunder serves it from the zone
pool rather than from a local device:

```yaml
resources:
  limits:
    thundercompute.com/gpu-a6000: 2
```

We are releasing a public Helm chart soon. For how the chart is built and why, see
[Kubernetes internals](/kubernetes-internals). For virtual machines, complete this
page then see [KubeVirt](/kubevirt).

<Note>
  GPU servers still need the Thunder-patched NVIDIA GPU driver before they can
  serve capacity. See [Requirements](/requirements) and
  [NVIDIA driver setup](/nvidia-driver).
</Note>

## Requirements

| | |
| --- | --- |
| Kubernetes `1.34+` | Manifests use `resource.k8s.io/v1`. The default configuration needs **no feature gates**. |
| Kubernetes `1.36+` | Required only for `resources.limits` requests. See [Feature gates](#feature-gates). |
| API token | Read, create, and delete on zones, servers, clients, and enrollment tokens. See [Authentication](/authentication#claims). |
| Egress to `get.thundercompute.com` | Nodes download the Thunder client library from here. Mirror it with `thunder.artifactBaseURL`. |

Managed services (EKS, GKE, AKS) are supported on `1.36+` with no control plane
configuration.

Only GPU-serving nodes need a local GPU. Nodes that run workloads do not.

### Workload images

Workload images need **nothing** added to them: no Thunder client, no `curl`, no
shell, and no root. A stock `ubuntu` image works unmodified.

When a container that claims a GPU is created, the daemon's CDI hook installs
`libthunder.so` and `/etc/thunder/config.json` into it, and enrolls it as a Thunder
client. The library is downloaded once per node, verified against the digest its
installer pins, and cached by digest, so only the first container on a node waits
for the download.

## Install

<Steps>
  <Step title="Create the namespace and API token secret">
    The chart never takes the token as a value, so it never reaches the Helm
    release history. Create the Secret first.

    ```bash
    export THUNDER_API_TOKEN='<token>'

    kubectl create namespace thunder-system \
      --dry-run=client -o yaml | kubectl apply -f -

    kubectl -n thunder-system create secret generic thunder-api \
      --from-literal=THUNDER_API_TOKEN="${THUNDER_API_TOKEN}" \
      --dry-run=client -o yaml | kubectl apply -f -
    ```
  </Step>

  <Step title="Label the GPU nodes">
    Only nodes that serve GPUs need labels, and only these two. The daemonset
    schedules onto them; nodes that merely run workloads need nothing.

    ```bash
    kubectl label node <node-name> thundercompute.com/node=true
    kubectl label node <node-name> topology.kubernetes.io/zone=<zone-name>
    ```

    <Note>
      The GPU model is detected on the host, not read from a label (see
      [GPU types](#gpu-types)), and the daemon verifies the GPU and driver
      version itself at startup.
    </Note>

    <Note>
      Thunder advertises the node's own IP (`InternalIP`, then `ExternalIP`) to
      clients. Override it only when clients reach the node on a different address,
      for example behind NAT:

      ```bash
      kubectl label node <node-name> thundercompute.com/advertised-ip=<reachable-ip>
      ```

      The address must be reachable by every server and client in the zone.
    </Note>
  </Step>

  <Step title="Apply the CRDs">
    Helm installs CRDs on first install but never upgrades them, so apply these
    before every install and upgrade.

    ```bash
    kubectl apply -f charts/thunder-device-plugin/crds/
    ```
  </Step>

  <Step title="Install the chart">
    ```bash
    helm upgrade --install thunder-device-plugin charts/thunder-device-plugin \
      --namespace thunder-system
    ```

    Point at a differently named Secret with `--set thunder.secretName=<name>`.
  </Step>
</Steps>

## Verify

```bash
helm test thunder-device-plugin -n thunder-system
```

The test waits for the operator to publish inventory, which is the end-to-end signal
that the chart reached the Thunder API. Then list what the cluster can serve:

```bash
kubectl get deviceclasses -l app.kubernetes.io/name=thunder-dra-driver \
  -o custom-columns=CLASS:.metadata.name,RESOURCE:.spec.extendedResourceName
```

```text
CLASS               RESOURCE
thunder-gpu-a6000   thundercompute.com/gpu-a6000
thunder-gpu-h100    thundercompute.com/gpu-h100
```

One class per GPU model, each with its own resource name. See
[Naming a GPU type](#naming-a-gpu-type).

## Requesting GPUs

| | Syntax | GPU type comes from | Requires |
| --- | --- | --- | --- |
| Extended resource | `resources.limits` | the resource name | `1.36+` |
| `ResourceClaim` | `count:` | the `DeviceClass` name | `1.34+` |

Both draw from the same zone pool, and both name a GPU model.

<Tabs>
  <Tab title="Extended resource">
    The simplest form. The scheduler generates the `ResourceClaim` for you.

    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: thunder-simple
    spec:
      containers:
        - name: tester
          image: ubuntu:24.04
          command: ["bash", "-lc", "nvidia-smi && sleep 3600"]
          resources:
            limits:
              thundercompute.com/gpu-a6000: 2
    ```

    <Note>
      Thunder GPUs never appear in `kubectl describe node`. The kubelet does not
      advertise them in `allocatable`; the scheduler resolves them. That is what
      lets one pool be shared across a zone instead of pinned to a node.
    </Note>
  </Tab>

  <Tab title="ResourceClaim">
    Use a `ResourceClaimTemplate` so Kubernetes creates and deletes one claim per
    pod. This form needs no feature gate. The `DeviceClass` names the GPU model.

    ```yaml
    apiVersion: resource.k8s.io/v1
    kind: ResourceClaimTemplate
    metadata:
      name: thunder-pod-gpu
    spec:
      spec:
        devices:
          requests:
            - name: gpu
              exactly:
                deviceClassName: thunder-gpu-a6000   # the class pins the model
                allocationMode: ExactCount
                count: 2                             # one device per GPU
    ---
    apiVersion: v1
    kind: Pod
    metadata:
      name: thunder-pod-gpu
    spec:
      restartPolicy: Never
      resourceClaims:
        - name: gpu
          resourceClaimTemplateName: thunder-pod-gpu
      containers:
        - name: tester
          image: ubuntu:24.04
          command: ["bash", "-lc", "nvidia-smi && sleep 3600"]
          resources:
            claims:
              - name: gpu
                request: gpu
    ```
  </Tab>
</Tabs>

Apply and inspect:

```bash
kubectl apply -f pod.yaml
kubectl get pod thunder-pod-gpu
kubectl get resourceclaims
```

## GPU types

Each GPU model gets its own `DeviceClass` and extended resource. These are generated
from Thunder inventory, so **Kubernetes labels never carry the GPU model**:

```text
1. thunderd detects the GPUs on the host        4x A6000
2. Thunder API inventory reports them           {gpuType: "A6000", gpuCount: 4}
3. operator groups inventory by zone + model    us-west-2a / a6000
4. operator creates the class and resource      thunder-gpu-a6000
                                                thundercompute.com/gpu-a6000
```

Step 1 happens during enrollment: the daemon runs the Thunder installer on the host,
and `thunderd` inspects the hardware and registers it. The daemon's own `nvidia-smi`
checks confirm only that a GPU and a recent enough driver are present; the model
comes from Thunder.

A model no zone has served before therefore becomes requestable within one reconcile
(default `60s`) of the node being **enrolled with Thunder** — adding a Kubernetes
node is not the trigger. Retiring the last GPU of a model removes its class and pool
the same way. Watch it happen:

```bash
kubectl get deviceclasses -l app.kubernetes.io/name=thunder-dra-driver --watch
```

<Note>
  Requesting a model you do not have yet leaves the pod `Pending` rather than
  failing, and it schedules by itself once one is enrolled.
</Note>

### Naming a GPU type

A zone can serve several models, and one Thunder client is enrolled with exactly
one model, so **every request names a model:**

```yaml
resources:
  limits:
    thundercompute.com/gpu-a6000: 2
```

The model is part of the resource name for extended resources, and part of the
`DeviceClass` name for `ResourceClaim`s.

## Oversubscription

How many GPUs a zone publishes is capacity policy read from the Thunder API, not a
chart setting. The operator applies each zone's oversubscription target per GPU
model:

```text
4 physical A6000s x 1.5 target  ->  6 published GPUs
```

Change the target in Thunder and the pool resizes on the next reconcile, with no
redeploy:

```bash
kubectl get resourceslices -l app.kubernetes.io/name=thunder-dra-driver \
  -o custom-columns=POOL:.spec.pool.name,TARGET:'.metadata.labels.thundercompute\.com/oversubscription'
```

A claim always gets whole GPUs; sharing is expressed by how many the zone
publishes. Targets round down so a target is never exceeded, and a missing target
falls back to `1`.

## Feature gates

The DRA APIs are GA in `1.34`, and everything the driver publishes uses only those,
so a stock `1.34+` cluster needs no gates. One optional capability does:

| Capability | Gate | Needed for |
| --- | --- | --- |
| Extended resources | `DRAExtendedResource` | `resources.limits` requests |

It is **beta and enabled by default from Kubernetes `1.36`.** On `1.34` and `1.35`
it is alpha and must be enabled explicitly; managed control planes do not expose
alpha gates, so upgrade to `1.36+` instead. Without it, use `ResourceClaim`s — they
need no gate at all.

### Checking a cluster

```bash
kubectl apply --dry-run=server -o yaml -f - <<'EOF'
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: thunder-extended-resource-check
spec:
  extendedResourceName: thundercompute.com/gpu-check
  selectors:
    - cel:
        expression: device.driver == "thundercompute.com"
EOF
```

The returned object must still contain `extendedResourceName`. If it is missing, the
cluster serves `ResourceClaim`s only. A missing gate is never an error: the field is
silently dropped.

<Accordion title="Enabling the gate on Kubernetes 1.34 and 1.35">
  Set it on the API server, scheduler, controller-manager, and **every kubelet**.
  A missing kubelet gate does not surface until a pod tries to start on that node.

  <Tabs>
    <Tab title="RKE2">
      Server config at `/etc/rancher/rke2/config.yaml`:

      ```yaml
      kube-apiserver-arg:
        - "feature-gates=DRAExtendedResource=true"
      kube-scheduler-arg:
        - "feature-gates=DRAExtendedResource=true"
      kube-controller-manager-arg:
        - "feature-gates=DRAExtendedResource=true"
      kubelet-arg:
        - "feature-gates=DRAExtendedResource=true"
      ```

      Worker config needs only the `kubelet-arg` block. Restart on each node:

      ```bash
      sudo systemctl restart rke2-server
      sudo systemctl restart rke2-agent
      ```
    </Tab>

    <Tab title="K3s">
      K3s takes the same keys, at `/etc/rancher/k3s/config.yaml`:

      ```yaml
      kube-apiserver-arg:
        - "feature-gates=DRAExtendedResource=true"
      kube-scheduler-arg:
        - "feature-gates=DRAExtendedResource=true"
      kube-controller-manager-arg:
        - "feature-gates=DRAExtendedResource=true"
      kubelet-arg:
        - "feature-gates=DRAExtendedResource=true"
      ```

      Agent config needs only the `kubelet-arg` block. Restart:

      ```bash
      sudo systemctl restart k3s
      sudo systemctl restart k3s-agent
      ```

      <Note>
        A K3s server that also runs workloads needs both the control-plane arguments
        and `kubelet-arg`.
      </Note>
    </Tab>

    <Tab title="kubeadm">
      Add the flag to the three static pod manifests in `/etc/kubernetes/manifests/`:

      ```yaml
      spec:
        containers:
          - command:
              - kube-apiserver
              - --feature-gates=DRAExtendedResource=true
      ```

      Repeat for `kube-scheduler.yaml` and `kube-controller-manager.yaml`. The
      kubelet restarts each static pod when its manifest changes.

      On every node, including workers, edit `/var/lib/kubelet/config.yaml`:

      ```yaml
      featureGates:
        DRAExtendedResource: true
      ```

      ```bash
      sudo systemctl restart kubelet
      ```

      <Warning>
        If a component already has a `--feature-gates` flag, extend that
        comma-separated list. A duplicate flag is ignored and the component starts
        without the gate.
      </Warning>
    </Tab>

    <Tab title="kind">
      ```yaml
      kind: Cluster
      apiVersion: kind.x-k8s.io/v1alpha4
      featureGates:
        DRAExtendedResource: true
      nodes:
        - role: control-plane
      ```
    </Tab>
  </Tabs>
</Accordion>

## Configuration

Every value is documented in the chart's `values.yaml` and validated against
`values.schema.json`, so a misspelled `--set` key fails the install rather than being
ignored. The values most deployments touch:

| Value | Default | Purpose |
| --- | --- | --- |
| `thunder.secretName` | `thunder-api` | Existing Secret holding `THUNDER_API_TOKEN` |
| `thunder.apiURL` | `https://registry.thundercompute.com` | Thunder API endpoint |
| `thunder.artifactBaseURL` | `https://get.thundercompute.com` | Where the Thunder client library is downloaded from |
| `thunder.telemetryURL` | `https://telemetry.thundercompute.com:2096` | Telemetry collector written into each container's client config |
| `operator.reconcileInterval` | `60s` | How quickly inventory and capacity changes are picked up |
| `nvidia.minDriverVersion` | `610` | Daemon refuses to enroll a node running an older driver |
| `kubelet.pluginDirRoot` | `/var/lib/kubelet/plugins` | Change on distributions that move the kubelet root |

### Serving artifacts from your own host

Nodes fetch `libthunder.so` from `thunder.artifactBaseURL`. Point it at a mirror, an
internal registry, or a staging host to run a different client build:

```bash
helm upgrade --install thunder-device-plugin charts/thunder-device-plugin \
  --namespace thunder-system \
  --set thunder.artifactBaseURL=https://artifacts.internal.example.com
```

The host must serve both `install.sh` and `libthunder.so`. The daemon reads the
digest `install.sh` pins and verifies the library against it before staging it into
any container, so a mirror that has drifted fails loudly rather than silently
serving the wrong build.

## Troubleshooting

| Symptom | Cause | Check |
| --- | --- | --- |
| Claims stay `Pending` | No pool for that GPU type | `kubectl get resourceslices -l app.kubernetes.io/name=thunder-dra-driver` |
| Resource name unknown | No node of that model enrolled | `kubectl get deviceclasses -l app.kubernetes.io/name=thunder-dra-driver` |
| `resources.limits` ignored | `DRAExtendedResource` off on `1.34`–`1.35` | [Checking a cluster](#checking-a-cluster) |
| Container fails to start with `createRuntime hook` in the message | Node cannot reach `thunder.artifactBaseURL`, or the served library does not match the pinned digest | `kubectl describe pod <pod>` |
| `nvidia-smi` reports the runtime is unavailable for ~30s after start | The node's `thunderd` has not yet picked up the new client from its check-in | Retry; it resolves without intervention |
| Pod stuck `ContainerCreating` | Daemon cannot prepare the claim | `kubectl -n thunder-system logs -l app.kubernetes.io/component=daemon` |
| Unknown resource name | Model not enrolled, or name misspelled | `kubectl get deviceclasses -l app.kubernetes.io/name=thunder-dra-driver` |
| Pool larger than the GPU count | Zone oversubscription target above `1` | [Oversubscription](#oversubscription) |
| No pools at all | Operator cannot reach the Thunder API | `kubectl -n thunder-system logs -l app.kubernetes.io/component=operator` |
